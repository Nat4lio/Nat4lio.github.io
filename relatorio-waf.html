Testing & WAF Deployment.

Black-box security assessment on OWASP Juice Shop v17.2.0 following OWASP WSTG v4.2 guidelines, followed by the implementation and validation of an Apache 2 + ModSecurity + OWASP CRS Web Application Firewall.

01Architecture

Testbed & Defense Topology

The project was conducted in two distinct phases over an isolated Host-only network (192.168.56.0/24). In Phase 1, the Kali Linux auditing client interacted directly with the vulnerable OWASP Juice Shop instance (Node.js / Express / Angular / SQLite) through OWASP ZAP 2.17.0 acting as an intercepting proxy.

In Phase 2, all external HTTP traffic was routed through port 80 on an Apache 2 reverse proxy running ModSecurity 2 and the OWASP Core Rule Set (CRS) in enforcement mode, isolating the backend on localhost:3000.

02Phase 1 · Offensive

Authentication Bypass via SQL Injection

Using OWASP ZAP's Spider, AJAX Spider, and FuzzDB Offensive payloads, the assessment covered all applicable OWASP WSTG v4.2 categories. By fuzzing the JSON email parameter on POST /rest/user/login, a critical SQL Injection vulnerability was exploited.

-- Vulnerable SQL query executed by the backend SELECT * FROM Users WHERE email = '' OR TRUE --' AND password = '...' -- Condition always evaluates to TRUE, returning the first record (admin@juice-sh.op)

Injecting the authenticated admin session into ZAP's Session Properties expanded the active scan coverage to 19,864 requests across /rest/admin and /rest/user, uncovering 26 total alerts including SQL Injection, Missing Anti-CSRF Tokens, JWT in localStorage, Stack Trace Disclosure (500 Internal Server Error), and missing clickjacking/MIME-sniffing headers.

03Phase 2 · Defensive

WAF Implementation & Custom JSON Inspection

To remediate vulnerabilities at the perimeter without modifying the application's source code, Apache 2 was configured as a Reverse Proxy with ModSecurity in blocking mode (SecRuleEngine On). Crucially, rule id:100001 was engineered to instruct ModSecurity to parse application/json request bodies — allowing the OWASP CRS to detect SQL injection payloads inside REST API login requests.

# 1. Hide Apache version & OS banner (Information Disclosure mitigation) ServerTokens Prod ServerSignature Off # 2. Inject Security Headers (Clickjacking & MIME-Sniffing mitigation) Header always set X-Frame-Options "SAMEORIGIN" Header always set X-Content-Type-Options "nosniff" # 3. ModSecurity & JSON Body Processor for REST API protection <IfModule mod_security2.c> SecRuleEngine On SecRule REQUEST_HEADERS:Content-Type "application/json" \ "id:'100001',phase:1,t:none,t:lowercase,pass,nolog,ctl:requestBodyProcessor=JSON" ErrorDocument 403 "<h1>WAF: Acesso Bloqueado pelo ModSecurity/OWASP CRS</h1>" </IfModule> # 4. Reverse Proxy to isolated Juice Shop backend ProxyPreserveHost On ProxyPass / http://127.0.0.1:3000/ ProxyPassReverse / http://127.0.0.1:3000/
04Validation & Results

Before vs. After WAF Comparison

Repeating the fuzzing attack and automated scans through port 80 confirmed that legitimate authentication attempts continued to reach the backend (401 Unauthorized), while SQL Injection payloads were intercepted and blocked immediately at the WAF layer with 403 Forbidden, cutting total active alerts from 26 to 13.
